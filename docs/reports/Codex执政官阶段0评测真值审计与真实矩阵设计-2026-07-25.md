# Codex 执政官阶段 0：评测真值审计与真实矩阵设计

日期：2026-07-25  
性质：只读基线审计结论；本报告不把夹具、canary 或历史进程记录写成真实能力证明。  
产品基线：`origin/main` 的 `d173ebb8521e2b0e8fcd805c426045a582b02048`（PR #51）。

## 结论

阶段 0 发现了一个所有后续真实样本共用的静态证据缺口，满足 PR A 的触发条件：现有 task ledger、attempt 和 capability receipt 不能完整记录真实矩阵与后续连接层对照所需的来源、连接方式、端到端时间、人工介入和独立验收器身份。

这不是 Qoder 或 CodeBuddy 的单次失败，也不是任务实例本身的问题。若不补齐，阶段 1 即使得到 `accepted`，也无法复核该样本是否来自真实需求、走了哪条连接路径、耗时是否可比、Codex 介入多少次，以及是否由同一独立验收器判定。因此不能直接进入阶段 1，也不能把旧 receipt 当作新矩阵样本。

## 现有材料的真值分类

| 条目 | 分类 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| `readonly-contract-map`、`readonly-lifecycle-trace` | 合同回归 | 只读任务的范围约束与回答可核对。 | 任一 provider 已能处理用户真实诊断。 |
| `bounded-test-fix`、`bounded-contract-doc` | 合同回归 | 材料注入、基线失败、不可变测试、写入范围和独立复跑链路。 | 用户真实 bug 修复能力；两题都是随包夹具。 |
| `fixed-ledger-regression`、`fixed-profile-regression` | 合同回归 | 固定命令与状态机没有倒退。 | worker 能可靠运行真实项目检查。 |
| `recovery-provider-rejection`、`recovery-partial-worktree` | 故障注入回归 | 失败不被自动重试、合并或误收货。 | provider 当前真实恢复能力。 |
| 既有 canary、marker、`process_exited` 记录 | 启动/过程证据 | 某条 CLI 曾启动并留下局部证据。 | 独立验收通过的真实任务族能力。 |
| 历史 experiment/plan | 不可采信历史，除非重新冻结输入并独立复跑。 | 发现候选问题和失败模式。 | 当前 provider tuple 的 accepted 样本。 |

## 已有静态底座

`origin/main` 已具备可复用的基础：

- edit 任务的材料模板、输入文件、基线失败命令、不可变路径和写入集合；
- provider tuple、权限 profile、generation 和 contract hash；
- completion、stdout/stderr、worktree、独立 Codex verdict 的分层；
- 失败分类、隔离 worktree、固定三条 accepted 才 qualified 的能力门；
- 最终 artifact、Release 和 stable 安装的不可变交付链。

这些机制保留。它们不自动把合成夹具升级为真实任务能力。

## PR A 的共同静态缺口

| 阶段 1/2 必需事实 | 当前情况 | 缺口后果 |
| --- | --- | --- |
| 任务来源类别与来源标识 | task/attempt schema 没有 `real_historical_issue`、`real_user_request`、`contract_regression` 等来源字段。 | 无法把真实任务与夹具/历史过程记录可靠分开。 |
| 连接方式 | provider tuple 记录 provider、CLI、model、权限，但没有 supervised CLI/text/JSON/stream-json/ACP/SDK/daemon。 | 阶段 2 无法做到只改变连接方式的同题比较。 |
| 真实时间线与端到端耗时 | watcher 有局部启动/退出事实，但 ledger attempt 在记录时把 `created_at`、`finished_at` 同时写为记录时刻，capability receipt 也没有时间线。 | 不能比较从派工到 Codex 接受的真实时间。 |
| 人工介入量 | ledger event 没有稳定 actor/介入类型，attempt/receipt 没有汇总。 | 不能比较 Codex 协调和恢复成本。 |
| 独立验收器身份 | task 有 `acceptance` 文本和 `required_checks`，receipt 只复制 checks；没有 verifier id/version/hash。 | 不能证明不同样本由同一独立验收逻辑裁决。 |

因此 PR A 应只补上述字段、传播与确定性回归：不更换 provider，不运行真实 worker，不把任何样本设为 accepted，不改变自动路由，也不新增公开能力承诺。

## 阶段 1 矩阵设计（待 PR A 合并后执行）

| 任务族 | 数量 | 真实来源要求 | 验收硬门 |
| --- | ---: | --- | --- |
| 只读诊断 | 2–3 | 已关闭的真实定位/解释问题；冻结起始 commit，worker 看不到修复提交。 | 答案与源码/独立核对一致，零 diff，明确报告不确定性。 |
| 受限改码 | 3 | 已修复的低风险历史 bug；原始失败、输入哈希、写入范围和独立 grader 预先冻结。 | 基线先失败、仅允许范围变更、从干净副本独立通过。 |
| 测试/恢复 | 2 | 真实的可复现失败或已知运营阻塞；不把故障注入自身当能力。 | 正确停止/分类、保存 completion/log/diff，无自动重试或合并。 |

每个实例在 PR A 后再从 `origin/main` 的隔离 worktree 准备，并在派工前完成 Codex 基线。Qoder 和 CodeBuddy 对同一任务族使用不同实例；同一时刻只允许一个写任务。每个运行必须记录：冻结输入与哈希、provider tuple、连接方式、起止时间、人工介入、stdout/stderr、completion、diff、验收器身份与 Codex verdict。

## 停止条件与下一步

1. 当前没有 provider tuple 被称为合格；没有真实 `accepted` 样本可进入能力画像。
2. PR A 是必要的，但它只需让字段贯穿开发者侧的 plan manager、watcher 产物、ledger、验收 receipt 与确定性回归，才能真实支持阶段 1。
3. 本次不改 MCP 对外工具、plugin runtime、安装路径、版本或公开能力；Codex 可在阶段 1 通过既有脚本登记每次矩阵的证据上下文。因此 PR A 保持普通治理 PR，不触发 Release。
4. 实现并验证 PR A 后，创建 `codex/` 分支提交/推送及中文 PR 材料；用户创建、审批并合并。合并后才创建阶段 1 的 disposable worktree 并运行真实矩阵。
