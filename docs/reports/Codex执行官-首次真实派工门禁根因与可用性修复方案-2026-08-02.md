# Codex 执行官：首次真实派工可用性与成本控制

日期：2026-08-02
状态：本报告的实现已纳入本次发布影响候选；发布前仍须完成候选 artifact 与真实受控任务验收。

## 一页结论

以前系统要求同一 worker 的同一任务族先积累 3 条成功记录，才允许正常派工。这条规则把“历史经验”错放成了“开始工作的许可证”。结果是：用户已经有一项范围、检查和验收都明确的真实任务，worker 却还没有启动就被挡住；每次产品发版又会因无关 generation/hash 变化让旧记录全部失效。

本次改为：完整、受控的真实用户任务可以直接派出；三条成功仅表示该 worker 身份已被充分观察，会影响推荐排序，不再作为派工门禁。失败仍留在隔离区，不会合并。不会为了凑记录自动创建会消耗 provider 积分的任务。

## 修复内容

1. 正常派工不再要求 3 条 accepted receipt。仍要求明确任务族、当前 readiness、允许/禁止路径、预算、检查、工作树与最终 Codex 验收。
2. worker 身份改为 provider、CLI、模型、权限、任务类型、连接方式和 runner 身份；不再把产品 generation 或整份 runtime contract hash 当作 worker 经验的身份字段。
3. `connection_mode` 与 runner hash 进入新 receipt。缺少这两个字段的历史 receipt 只保留追溯价值，不能迁移成新身份证据。
4. 从计划派发真实任务时，若没有手写证据上下文，控制面会在 worker 真正启动后以实际连接方式自动写入该任务的来源和验收上下文。不会要求模型手填八个 hash 字段。
5. `validation_only` 任务不能通过普通计划派发调用外部 provider；它应使用本地 fixture 或由用户明确转为真实任务。
6. dry-run 明确显示“预演通过，未启动”，并保证没有 job id；不再误报“已派发 worker”。

## 未改变的安全边界

- 不读取、输出或迁移认证资料、provider 数据库、token 或 cookie。
- 不派认证、生产、不可逆外部动作；外部网络按任务合同控制。
- 编辑任务只在隔离 worktree；验收前不会进入主项目。
- `completion`、范围差异、独立检查和 Codex 验收缺一不可。失败、超时、越界或无 completion 不会成为 accepted 证据。

## 验收标准

- 0 条历史 receipt 的完整真实计划任务能通过无副作用的 dry-run，且 dry-run 不创建 job、不宣称已启动。
- 3 条 receipt 只把画像标为充分观察，不再影响派工许可。
- generation/runtime contract 变化不再切断相同 worker 身份的画像；模型、权限、连接或 runner 变化仍形成不同画像。
- `validation_only` 不会自动消耗 provider credits。
- 从最终发布 artifact 运行确定性矩阵，并以一次本来就要做的受控真实任务验证用户路径；不额外创建热身任务。

## 证据依据

本地根因来自 `scripts/dispatch/test-codex-praetor-capability-evidence.ps1`、`mcp/src/capability-profiles.ts` 与 `mcp/src/tools.ts`：前者曾强制 3 条 exact tuple，tuple 包含 generation/runtime hash 却没有 connection mode；后者在计划没有 evidence context 时无法进入已有 bootstrap，dry-run 又复用了“已启动”的展示。

外部佐证：OpenAI Agent Evals 建议把真实 trace 转为可重复 eval 数据，而不是反复烧真实任务；Temporal Worker Versioning 按兼容性和渐进切换管理版本，而非每次版本清零经验；Claude Code 与 OpenHands 都将自动执行的关键约束放在 sandbox/runtime 边界，而不是以重复确认替代隔离。
