# Codex 执政官模式真实派工闭环缺陷与单 PR 修复规划

日期：2026-08-07
性质：内部考古、外部调研和单 PR 实施记录；本轮修复控制面合同并完成确定性验收，不把候选安装或真实 provider 结果伪装成已完成。

## 先说结论

这次不是“任务不能拆”，也不是 Qoder/CodeBuddy 已经证明不可用。真实问题是：**执政官模式只完成了路由判断，没有继续走到计划、预演和真实派工**。

目标对话在用户说“开启执政官模式”之后，实际出现了 7 次 `codex_praetor_route_intent`，但出现了 0 次：

- `codex_praetor_dispatch_dry_run`
- `codex_praetor_dispatch_plan_task`
- `codex_praetor_dispatch`
- worker `job_id`
- `execution_worktree`

所以那几轮没有花 worker 额度，也没有失败的 worker；它们只是被控制面留在“判断阶段”。这与用户要的“把能拆的工作拆出去”不一致。

本轮已经完成的即时动作：

- 两份仓库 Skill 已统一正式触发词为“执政官模式”；
- Skill 已明确 `route → plan → dry-run → dispatch` 是连续流程，`route_intent` 完成不等于已派工；
- Skill 已明确大任务要拆成 Codex 保留部分和 worker 部分，不能因为整体复杂而全部回退给 Codex。
- `route_intent` 已返回结构化继续合同：`dispatch_required`、`next_required_tool`、`delegable_subtasks`、`codex_reserved_tasks` 和 `blocking_reason`；外部 worker 路由不再只有自然语言建议。
- 已加入 route-only 回归：外派路由必须产生下一工具和可拆范围；用户明确要求 Codex 自己处理时必须返回可审计阻断，不得误派。

但当前安装缓存仍是旧 Skill，源码与缓存 SHA256 不一致。因此，**要让新对话真正使用新合同，还必须在同一个发布影响 PR 中完成 Skill 发布、缓存同步、宿主刷新和新任务 `runtime_info` 核对**。

最终建议：做一个发布影响 PR，修复“模式触发、可派工性判断、连续派工状态机、部分外派、回执可观测性、安装生效链”这一组共同根因；不拆成多个零散 PR。

## 2. 哪些任务可以拆，哪些必须由 Codex 保留

### 2.1 明显可外派的任务

下列任务具备“边界清楚、可独立验收、可以只读或在隔离 worktree 修改”的条件：

| 任务 | 推荐模式 | Codex 保留什么 |
| --- | --- | --- |
| 只读代码考古：账号调度、资源键归属、历史报告与代码对照 | `readonly/local_audit` | 事实冲突裁决和最终报告 |
| 确定性测试执行：已有命令、固定输出 marker、无生产副作用 | `readonly/test_execution` | 解释失败、决定是否继续 |
| schema、能力清单、文档索引、回执关系检查 | `readonly/local_audit` | 公开承诺和发布结论 |
| 单一根因的小范围公共代码修复 | `edit/code_change` | 规划、worktree 边界、合并和最终验收 |
| 低风险证据候选整理 | `readonly/external_research_support` | KnowledgeRadar 主证据、交叉核验和结论 |

这类任务不需要 worker 访问认证文件、cookie、provider 数据库、生产环境或不可逆外部动作。

### 2.2 必须由 Codex 保留的任务

- 总体任务拆分、依赖关系和最终方案选择；
- 用户登录、扫码、验证码、认证、额度和风控处理；
- 生产环境、公开发布、PR 合并、版本/tag/Release 和下载交付；
- 多 worker 结果冲突时的最终取舍；
- 最终验收、失败分类和是否允许进入主线。

### 2.3 不能把“复杂”当成不可拆

本次对话里的“研究＋修复＋验证”是复合任务，但可以拆成：

1. Codex 保留总体计划和敏感/最终环节；
2. worker 先做只读考古或确定性测试；
3. 若有局部代码修复，再单独给一个隔离 worktree 任务；
4. Codex 汇总结果并验收。

正确的判断不是“整个任务复杂，所以不派”，而是“哪些子结果可以独立派、哪些不能派”。

## 3. 为什么停在 route_intent

### 3.1 当前代码把 route 设计成分类器，不是编排器

本地证据：

- `mcp/src/route-intent.ts:14-25` 只定义了 Praetor/provider 术语；没有“执政官模式”正式词表；
- `mcp/src/route-intent.ts:134` 和 `:171` 对外返回的下一步只是“运行 `codex_praetor_dispatch_dry_run`”；
- `mcp/src/server.ts:164-175` 注册的 `codex_praetor_route_intent` 只是分类工具；
- `mcp/src/server.ts:203-219`、`:415-432` 分别注册 dry-run 和计划任务派工，但没有代码把 route 的结果自动串到后两个工具；
- `mcp/src/tools.ts:56-64` 的 `routeIntentTool` 只返回分类结果；
- `mcp/src/tools.ts:1187-1244` 的 `dispatchPlanTaskTool` 只有在上层明确调用时才会检查 pending 计划并启动 worker。

因此，“route 返回 external worker”只是建议，不会自动产生 plan、dry-run 或 job。

### 3.2 Skill 合同曾经允许把 route 当作终点

旧版 Skill 只写“每个实质任务先 route”，并把“不能外派时由 Codex 自己完成”放在同一层，没有要求：

- route 指向外部 worker 后必须继续 dry-run；
- dry-run 通过后必须继续 dispatch；
- 只有具体阻断才能回退；
- 大任务必须寻找可拆子任务。

这使得模型可以合法地完成 route，然后把整个任务留在主线程；从工具账面看“模式被调用了”，从产品目标看“根本没有派工”。

### 3.3 “没有 evidence_context”曾经是错误的总闸门

既有报告《Codex执行官-首次真实派工门禁根因与可用性修复方案-2026-08-02》已经记录过同类问题：

- 真实、只读、范围明确的任务因为 `evidence_context=null` 没有启动 worker；
- 这是控制面门禁问题，不是网络、账号、worktree 或 provider CLI 故障；
- 每次产品版本变化还会因 generation/runtime SHA 变化而误使历史证据失效；
- “满 3 条真实成功才允许派工”应降级为观察标签，不能阻挡第一件真实工作。

本次不是完全同一个代码分支上的 `evidence_context` 复现，但属于同一类根因：**前置状态被当成启动终点，而不是用于决定如何安全启动首个受控任务**。

## 4. 已发现但未暴露为“失败”的问题

### 4.1 触发词、源码、安装缓存三处不一致

- 仓库两份 Skill 已改为“执政官模式”；
- `mcp/src/route-intent.ts` 仍没有该词；
- 当前安装缓存 `C:\Users\ga990\.codex\plugins\cache\personal\codex-praetor\0.16.29-alpha\skills\codex-praetor\SKILL.md` 仍只有“执行官模式”；
- 源码 Skill SHA256：`D0F5FFC5E6F62A6D4524D5789F65EA2680F1E92FBC4C4B92C7A778EB0F3BFCC7`；
- 安装缓存 SHA256：`8602FE186D6B6CB090E81945068E2F8E0F9F44E9C0B956E115F2C1250DA3BE88`。

这会造成“源码看起来修好了，但新对话仍按旧 Skill 工作”。

### 4.2 没有结构化的可派工性判定（已修复）

当前有 route、provider operations、explainable route 和 dispatch 工具，但没有一个明确的“可派工合同”输出：

- `delegable_subtasks`：可拆出的子任务；
- `codex_reserved_tasks`：必须保留的部分；
- `blocking_reason`：真实阻断原因；
- `next_required_tool`：下一步必须调用哪个工具；
- `dispatch_required`：是否必须继续派工。

缺少这个中间结果，模型很容易把“整体任务不能全部外派”误解为“整件事都不能外派”。本 PR 已在 `RouteDecision` 中补齐这些字段，并通过 MCP 自测覆盖外派、研究、明确自留和普通直做四类结果。

### 4.3 没有连续状态机和硬性推进断言（Skill 合同已加固）

MCP 运行时仍不能代替 Codex 宿主自动调用后续工具，但 Skill 与 route 返回已共同形成可审计的推进合同：

`route_decided → plan_created → contract_checked → dispatch_started → completion_received → supervisor_verified`。

route 返回 external worker 后必须检查 `dispatch_required=true` 和 `next_required_tool`；若没有后续调用，属于控制面未履约，不得写成“已派工”。真实 job 仍以 `job_id`、`execution_worktree` 和 started 回执为准。

### 4.4 真实派工证据虽然有定义，但缺少用户可见的短回执

代码层面已经要求 `job_id`、`execution_worktree` 和 started 状态，然而没有统一的短回执告诉用户：

- 这是预演还是实际启动；
- 为什么允许或阻断；
- 使用哪个 provider/model/连接；
- 下一步是等待 completion 还是需要用户登录/切换节点。

用户看到“已返回”时，无法判断是否真的花了额度、是否创建了 worktree。

### 4.5 provider 文档的“缺失”与“不可用”没有统一成可行动状态

`docs/provider-notes/qoder.md` 和 `codebuddy.md` 已明确：

- CLI 必须安装并登录；
- doctor 不读取认证状态；
- 真实派工前要有只读 canary；
- provider 缺失时，route/planning/dry-run 仍可用，真实派工禁用。

但派工链还缺一个统一的 readiness 结果，把“未安装”“未登录”“模型不在 allowlist”“连接失败”“额度不足”“当前任务不允许”分开返回；否则上层只能看到一个笼统阻断。

## 5. 外部调研得到的可借鉴结论

本轮使用 KnowledgeRadar 原生 MCP，研究任务：`kr-research-57d20cc6fc3a0781`，最终状态 `accepted_for_decision`，质量状态 `pass`。

### 5.1 OpenHands：组件和生命周期分层

官方文档：<https://docs.openhands.dev/sdk/arch/overview>

官方架构把 Agent、Conversation、Tool、Workspace、Events、Security、Lifecycle 分开；本地 Workspace 与 Remote/Sandbox Workspace 分开，并通过事件和状态管理执行过程。

对本项目的启示：路由推荐、执行环境、状态事件、验收不能混成一个“route 返回值”。

### 5.2 Codex Subagents：主 agent 拆分，子任务独立执行，结果回收

官方文档：<https://developers.openai.com/codex/concepts/subagents>（当前页面重定向到官方 ChatGPT Learn 页面）

官方说明：复杂任务可以拆成并行或独立子任务；主 agent 负责拆分和汇总；每个子 agent 有独立 thread；UI 展示状态和结果；并行写入要谨慎，子 agent 会增加 token 成本。

对本项目的启示：外派要以独立、可验收的子结果为单位；不能为了“看起来用了多 agent”而把所有工作都并行化。

### 5.3 CrewAI：Flow 是持续状态机，不是一次分类

官方文档：<https://docs.crewai.com/en/concepts/flows>

官方说明：Flow 用 start/listen/router 连接多步任务，带唯一状态 ID、结构化状态、持久化、恢复和 usage metrics。

对本项目的启示：应把 route 后续动作和状态持久化，不能依赖模型自行记住“下一步要调用 dispatch”。

### 5.4 AutoGen：结构化 handoff 和终止条件

官方文档：<https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/swarm.html>

官方说明：agent 通过结构化 `HandoffMessage` 把任务交给另一个 agent；接收方继续共享上下文；通过 termination condition 结束；模型必须支持 tool calling，且并行 tool calls 可能产生意外行为。

对本项目的启示：handoff/dispatch 要是结构化工具调用和状态，而不是自然语言暗示；同时保留并行写入和模型能力的限制。

### 5.5 CodeBuddy：连接和版本事实必须显式

官方文档：<https://www.codebuddy.ai/docs/zh/cli/installation>

官方文档确认：Node.js 安装路线、原生二进制路线、Windows x86_64 支持、配置目录、自动更新开关和 `codebuddy --version` 验证。它还提醒多个安装来源会导致执行旧版本。

对本项目的启示：provider identity 必须包含实际命令路径、版本和连接方式；不能只看产品版本号或“命令存在”。

### 5.6 Qoder：本轮只得到兼容索引，不作超范围结论

官方入口：<https://docs.qoder.com/en/cli/quick-start>

本轮页面解析到兼容入口和文档索引，没有拿到足够的完整 CLI 调用正文。因此本报告不声称 Qoder CLI 的具体参数、ACP/SDK 能力或认证行为；这些要在 PR 前用本机 CLI 和官方页面详情继续核实。

## 6. 单 PR 的最终修复方案

### 6.1 PR 目标

让用户说一次“开启执政官模式”后，后续每项实质任务都遵循：

`识别 → 拆分 → 形成合同 → 预演 → 真派工 → 回执 → Codex 验收`。

如果整体任务有一部分不能外派，仍然先把可外派部分派出去；只有明确阻断才由 Codex 接管，并把阻断写进回执。

### 6.2 修改范围

1. **Skill 与触发词**
   - 保留“执行官模式”兼容别名；
   - 正式触发词统一为“执政官模式”；
   - Skill 镜像、插件包、安装缓存发布路径必须一致；
   - 新任务首步用 `runtime_info` 核对已加载的是新 Skill/新 runtime。

2. **可派工性判定**
   - 新增结构化决策：`delegable_subtasks`、`codex_reserved_tasks`、`blocking_reason`、`next_required_tool`；
   - 判断“子任务”而不是只判断“整件事”；
   - 只读、固定测试、局部修改、候选证据整理默认进入可拆候选；认证、生产、发布和最终裁决默认保留。

3. **连续状态机**
   - route 返回 external worker 时，必须进入 plan/dry-run；
   - dry-run 通过后自动进入 dispatch，除非有结构化阻断；
   - 断言 `route=external_worker` 时不能以“只 route 完成”结束；
   - 每个状态写入可恢复的计划/事件，不靠模型记忆下一步。

4. **首单与证据门禁**
   - 不因 `evidence_context=null` 或未满 3 条而拒绝边界清楚的首个真实任务；
   - 3 条成功只作为观察标签；
   - provider readiness、连接、模型、权限、失败冷却、硬范围仍是硬门；
   - `generation_id`/整体 runtime SHA 不得无条件让 worker 身份证据失效；`connection_mode`、runner/CLI identity、模型和权限变化必须能精准失效。

5. **真实回执与可观测性**
   - 预演明确返回“未创建 job”；
   - 真实派工必须返回 `job_id`、`execution_worktree`、provider、model、connection_mode、started 状态；
   - 明确显示“本次是业务任务还是验证专用任务”；
   - completion、stdout/stderr、worktree diff 和 Codex 验收分开记录。

6. **provider readiness**
   - 把 CLI 缺失、未登录、模型不允许、连接失败、额度/风控、合同不完整分成不同 failure class；
   - readiness 只提供状态和下一步，不读取或输出认证资料；
   - 没有 provider 时，允许 route/plan/dry-run，但不能把它们说成真实派工。

7. **测试和发布**
   - 增加 route-only 回归：external route 必须产生 dry-run 或结构化阻断；
   - 增加首单 bootstrap、evidence_context 缺失、provider readiness 各失败类 fixture；
   - 增加部分外派测试：敏感部分留在 Codex，普通部分创建真实 job；
   - 增加 Skill 源码→插件包→安装缓存→新任务 runtime_info 的一致性检查；
   - 只在隔离候选中做最低必要真实 provider 任务，不为凑次数额外烧额度。

### 6.3 不纳入本 PR

- 不把 worker 变成无限权限或通用多代理平台；
- 不自动读取、迁移或修改认证、cookie、provider 数据库；
- 不把公开发布、PR 合并、生产操作交给 worker；
- 不重做 Qoder/CodeBuddy 连接层；如果 CLI/ACP/SDK 要替换，另开技术路线决策，不混入本 PR；
- 不因为单个 provider 暂时不可用就伪造 readiness 或重试到额度耗尽。

## 7. 通过标准

### A. 模式和安装

- 用户说“开启执政官模式”后，下一项实质任务能在新任务中读取到新 Skill；
- 源 Skill、插件 Skill、兼容镜像、安装缓存 hash 一致；
- `runtime_info` 与候选 receipt 的版本、generation、runtime contract 一致。

### B. 正常派工

- 一项明确的只读考古任务：route → plan → dry-run → dispatch；
- 真实结果包含 `job_id`、`execution_worktree`、completion；
- Codex 能根据 stdout/stderr、worktree 状态和检查结果给出 accepted/rejected；
- 主项目工作树没有被 worker 改动。

### C. 部分外派

- 复合任务至少拆出一个 worker 子任务；
- Codex 保留敏感/整合部分；
- 不能以“整体复杂”直接返回 no_delegation。

### D. 失败和成本

- provider 缺失、未登录、连接失败、额度不足分别返回不同原因；
- dry-run 不创建 job；
- 不再为凑 3 条自动创建验证任务；
- 失败任务不能 accepted、不能进入能力证据、不能进入主线。

### E. 回归

- route-intent、dispatch dry-run、计划任务、provider readiness、回执 schema、Skill 同步和安装生效链均有确定性测试；
- 真实 provider 只在连接/权限/任务合同确实变化时做一次最低必要现场验证；
- PR CI 之外，候选安装和新任务 `runtime_info` 必须通过后才可发布。

## 8. 执行顺序（一个 PR）

1. 冻结当前主线和现有用户修改，不清理、不 reset。
2. 先补结构化可派工性决策和状态机 fixture，证明 route 不会再成为终点。
3. 修 Skill、路由词表、计划/dispatch continuation 和回执 schema。
4. 修首单/evidence 门禁和 provider readiness 分类。
5. 同步两份 Skill、插件包和安装路径，构建带 SHA 候选。
6. 跑一次确定性候选矩阵；只对受影响 provider tuple 做最低必要真实任务。
7. 在隔离 Desktop 环境安装候选，刷新宿主，新任务先 `runtime_info`，再做一次最小真实派工。
8. 生成 candidate receipt；PR CI 只复核同一候选 artifact。
9. 合并后只提升同一 artifact，不重新打包；公开交付后核对下载 SHA。
