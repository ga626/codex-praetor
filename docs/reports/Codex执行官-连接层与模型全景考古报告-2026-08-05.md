## 先说结论

1. **Qoder 以前确实成功过。** 不是所有记录都是假的：2026-07-31 有一条真实的 Qoder `code_change`，它修改了一个受限文档，留下了实际 Git diff、13 次工具事件、最终结果和独立检查。
2. **但今天失败的 Qoder 组合已经不是当时的组合。** 当时是 Qoder Agent SDK `1.0.15` + 本机 Qoder CN CLI `1.0.45`；现在产品升级为 SDK `1.0.17`，这个 SDK 包声明配套 CLI 为 `1.1.11`，但本机仍是 `1.0.45`。本次真实代码修改任务启动后 3 分钟没有一条结构化事件、没有输出、没有 diff，已被正确拒绝。
3. **不能据此说“SDK 从来不能用”。** 历史真实成功反驳了这个说法。更严谨的结论是：**“全球 Qoder Agent SDK 被拿去驱动 Qoder CN 嵌入式 CLI”没有稳定的、版本受控的兼容承诺；升级后已出现实测失效。** SDK 升级与失败高度相关，但还不能在没有对照试验的情况下断言它是唯一根因。
4. **Qwen3.8-Max 已经正式上线，且本机账号可枚举到它；当前产品却仍把 Qwen3.7 写死。** 所以“为什么还在用 3.7”的直接答案是：不是模型不存在，而是项目配置、Skill、adapter 描述和 tier 路由还没有更新。
5. **当前不应合并 PR #88，也不应提交工作树中那套“Qoder CN 改走 stream-json”的未完成改动。** 它方向正确，但只接上了“启动 worker”这一段；进度、取消、MCP 展示、readiness、证据和发布候选验收还没有全链路接上。

最终建议不是继续给现有 SDK 打补丁，而是明确分开三条路线：

| 场景 | 应用路线 | 当前结论 |
| --- | --- | --- |
| 这台机器安装的 Qoder CN / QoderWork CN CLI | Qoder CN 自己的 `--print --output-format stream-json` | 官方支持，最符合本机；尚未完成产品级接入与验证 |
| 未来单独安装的全球 Qoder CLI + PAT / 全球登录态 | Qoder Agent SDK | 保留为独立可选 adapter；不能再自动拿 Qoder CN 二进制冒充它的 CLI |
| 腾讯 CodeBuddy / WorkBuddy | ACP | 仍有最近的真实成功证据；模型登记需要重新握手核对，但没有证据显示 ACP 本身已经失效 |

## 3. 连接层全景：现在每一步实际怎么走

### 3.1 产品的主链路

```text
自然语言触发 Skill
  -> Codex Praetor MCP 工具（mcp/src/tools.ts）
  -> PowerShell 派工器（scripts/dispatch/invoke-codex-praetor.ps1）
  -> 读取本机 tier / 模型 / CLI 配置
  -> 建立隔离 worktree 与任务合同
  -> 选择 provider adapter
       Qoder: Node Qoder SDK runner -> 配置中的 CLI
       CodeBuddy: Node ACP runner -> CodeBuddy CLI ACP
  -> watcher 读取 session / stdout / diff，写 completion
  -> ledger / readiness / MCP 状态展示
  -> Codex 独立验收
```

产品真正依赖的不是“模型名称”一项，而是下列 tuple：

```text
provider + CLI 文件/hash + CLI 协议 + adapter/runner hash + 模型 ID
+ 权限模式 + task_kind + 任务合同版本
```

其中任何一项换掉，都不能借用旧成功记录。

### 3.2 三种 Qoder 路线不能混用

| 路线 | 官方工作方式 | 能否复用本机 Qoder CN 登录态 | 对本项目的判断 |
| --- | --- | --- | --- |
| Qoder CN CLI | `--print`，`text/json/stream-json` 输出 | 可以 | 本机应优先研究的路线 |
| 全球 Qoder Agent SDK | Node `query()`，SDK 控制的 stdio / `qodercli` 运行时，支持 SDK 事件 | 仅官方定义的全球 `qodercli` 登录态或 PAT | 不能再假定可直接套在 CN `qoderclicn-legacy.exe` 上 |
| Qoder CN Cloud Agents | PAT + Agent + Environment + Session + SSE | 不可直接复用本地 CLI 登录态 | 是独立的云端产品路线，不是本次本机修复的低成本替代 |

官方 Qoder CN CLI 文档明确给出 `--print` 和 `--output-format text/json/stream-json`；也明确说明 SDK 是另一种由宿主处理权限回调的模式。全球 SDK 文档则写明使用 `@qoder-ai/qoder-agent-sdk`、PAT/全球 `qodercli` 与 SDK 消息流。Cloud Agents CN 另需 PAT、云端 Environment 和 SSE 事件流。

因此此前的结构性问题是：**产品把“Qoder CN CLI 的可执行文件”塞给“全球 Agent SDK 的 `pathToQoderCLIExecutable`”。** 这不是一个被官方承诺的适配关系。

### 3.3 CodeBuddy 路线的现状

CodeBuddy 当前走 ACP：Node runner 与 CLI 使用 JSON-RPC NDJSON 通信，runner 持有文件和受限终端代理，watcher 能理解 ACP 的结构化事件、边界拒绝与取消。

本机版本为 `2.115.0`，它的 `--help` 明确支持：

- `--acp` 和 `--acp-transport stdio`；
- `--output-format stream-json`；
- `--model` 固定模型 ID；
- `--allowedTools` / `--disallowedTools`。

所以 ACP 本身有直接本机证据，不需要因为 Qoder 出问题而推倒重来。

但这里还有一个待核对点：本机 help 列出的当前模型 ID 与项目把 `hy3` 作为默认 tier 的清单并不完全相同；另一方面，同一 CLI hash 的 ACP 历史任务确实用 `hy3` 成功。因此现在不能草率地把 `hy3` 删除或断言失效。正确下一步是做一次**不产生代码修改的模型能力握手**，把 CLI 实际接受的 ID、账号可见模型和项目白名单写成一份最新事实表。

## 4. 模型事实：为什么现在还在用 3.7

### 4.1 本机实测

本机 Qoder CN CLI：

```text
版本：1.0.45
--list-models：Auto、Qwen3.8-Max、Qwen3.7-Max、Qwen3.7-Plus、
Qwen3.6-Flash、DeepSeek-V4-Pro、DeepSeek-V4-Flash、GLM-5.2、
Kimi-K2.7-Code、MiniMax-M2.7
```

这说明两件事：

1. `Qwen3.8-Max` 对当前账号/CLI 的模型枚举是可见的；
2. “本机 CLI 太旧，所以肯定根本看不到 3.8”这个说法不成立。

### 4.2 官方事实

Qoder 官方在 2026-08-03 发布 `Qwen3.8-Max`，说明它适用于 Qoder CLI，并给出夜间 `22:00–08:00` 的 `0.5x` 折扣；官方也要求更新到最新版本后在模型选择器中使用它。

这说明 3.8 是真实存在的正式能力，但并**不**自动推出“当前 Codex Praetor 应当马上把所有任务切到 3.8”。模型升级、CLI 升级和连接层替换必须分开验证，否则一次失败无法知道是哪一层造成的。

### 4.3 项目为什么仍运行 3.7

当前本机配置 `%USERPROFILE%\.codex\codex-praetor.local.json` 和仓库示例都只允许：

```text
Qoder: Qwen3.7-Plus, Qwen3.7-Max
CodeBuddy: hy3, deepseek-v4-flash, deepseek-v4-pro
```

Skill 和 `config/provider-adapters/qoder.json` 也复制了 Qoder 3.7 白名单。于是即使 CLI 能看到 3.8，派工器仍会按策略拦住它或根本不把它选为 tier。

这是**配置过时**，不是“模型不可用”的证据。也不应把用户的“3.8 很便宜/有折扣”写成固定承诺：官方活动、账户资格、可领次数和时段都会变化，必须以用户账号的 `--list-models` 和用量面板为准。

## 5. 已确认的问题与可能冲突

### A. 已确认：Qoder CN 与全球 SDK 被错误地当成同一接入物

证据：当前 runner 固定调用 `qodercliAuth()` 和 SDK 的 `query()`，同时把 `qoderclicn-legacy.exe` 传为 SDK CLI 路径；官方文档却分别描述了 CN CLI 的 print 协议与全球 SDK 的运行模式。

影响：这是当前 Qoder 代码修改失败的首要排查方向。

### B. 已确认：未提交的 stream-json 改动还不是全链路实现

它已增加“根据二进制路径选 Qoder CN direct stream-json”的启动逻辑，但以下地方仍不知道或不认识新 connection mode `supervised_cli_stream_json`：

- `mcp/src/tools.ts` 的连接名称展示、session 读取、bootstrap 允许列表和默认回退；
- `watch-codex-praetor-job.ps1` 的进度/停滞/取消语义；
- readiness、capability evidence、用户 UI 所需的结构化状态；
- plugin bundle、skill 镜像和候选 Release artifact 的同步合同。

同时，新增的测试只检查源文件里有没有几段字符串。它能证明“有人写了分支”，不能证明“CN CLI 真能完成任务、状态能被解析、取消能恢复、证据能正确记录”。所以绝不能把它当通过凭证。

### C. 已确认：模型登记散落在多个位置

同一模型白名单至少出现在：本机 local config、仓库 example config、provider adapter JSON、Skill 文本、以及发布 bundle 生成物。现在没有一个单一事实源驱动其他副本。

影响：即便只更新一处为 3.8，也很容易出现“界面说可用、派工器拒绝”或“源码改了、安装包没改”的情况。

### D. 已确认：SDK 的配套 CLI 版本字段没有进入兼容性门禁

`@qoder-ai/qoder-agent-sdk` 包内有 `qoderCliVersion`，但项目只记录了 CLI 文件 hash，没有在启动前判断“这是哪一种 Qoder CLI、SDK 声明的版本是多少、是否是支持组合”。

影响：依赖升级可以悄悄改变 SDK 与 CLI 的协议假设，直到真实任务无输出才暴露。

### E. 需要验证：CodeBuddy 模型帮助文本与历史 `hy3` 成功证据不一致

这是一个“证据相冲突”而不是“已经坏了”的问题。近期同 hash 的 ACP 回执证明 `hy3` 实际跑过；当前 help 的模型清单却更偏向另一组模型。应先做能力握手并保存输出，再决定更新白名单，不能靠猜测改配置。

### F. 正常但容易误解：源码、副本与安装包不是逐文件相同

`mcp/src` 是源码，`plugin/mcp/dist` 是打包后的自包含运行时；它们 hash 不同在结构上是正常的。真正要检查的不是“两个文件是否字节相等”，而是发布候选是否从当前 source tree 构建、是否把需要的 runner 和 Skill 同步到同一 ZIP、以及 candidate receipt 是否绑定该 ZIP SHA。这个项目已有这类发布合同；新增连接层时必须把新 mode 纳入合同，而不是简单复制文件。

## 6. 推荐的最终技术路线

### 6.1 Qoder：按产品形态选 adapter，不再按品牌名选 adapter

```text
检测到 Qoder CN CLI (qoderclicn)
  -> Qoder CN direct CLI stream-json adapter

检测到官方全球 Qoder CLI 且兼容版本 / 登录方式满足 SDK 要求
  -> Qoder Agent SDK adapter

需要云端并行、用户明确提供 PAT 与云端 Environment
  -> 独立 Cloud Agents adapter（未来能力，不混进本机 CLI 首用流程）
```

这三条都可以保留，但必须各自拥有独立的：CLI/SDK identity、模型目录、事件解析、取消、readiness、能力证据和发布验收。不能共享“Qoder 已通过”这一张泛化通行证。

### 6.2 Qwen3.8-Max：应纳入路线，但排在连接层之后

建议顺序：

1. 先用当前已经存在的 `Qwen3.7-Plus` 验证 Qoder CN direct stream-json 的**协议与控制面**；这样失败时能明确归因于连接层，而非新模型；
2. 协议完成一次受限代码修改验收后，再在同一合同下只替换模型为 `Qwen3.8-Max`；
3. 两者都成功后，才更新默认/强档 tier、优惠说明与用户可见模型目录；
4. 折扣和 credits 仅显示为账号/时段相关信息，不固化为产品保证。

### 6.3 CodeBuddy：保持 ACP，先核对模型目录

不改 ACP 架构；只补一条轻量的本机能力握手，把 CLI `--help`、实测接受模型和账号可见模型写入版本化 evidence。之后再决定 `hy3`、`deepseek-v4-*` 及本机 local config 里的其他候选该如何分层。

## 7. 下一阶段验证方案（本报告不执行）

目标不是“再跑很多次”，而是用最少的真实调用回答每一个会影响路线的判断。

| 阶段 | 要回答的问题 | 方法 | 通过标准 | 失败后的动作 |
| --- | --- | --- | --- | --- |
| 0：静态闭环 | 新 adapter 是否在所有控制面都有定义 | 检查 schema、MCP 展示、watcher、readiness、evidence、bundle、Skill、release contract | 新 mode 没有任何旧默认回退或漏网副本 | 先补全代码，不跑 worker |
| 1：Qoder CN transport | CN direct stream-json 能否产生可解析的启动、工具、结果、取消事件 | 一个隔离、只读、无网络、固定 3.7 的最小任务 | 有结构化事件、成功结果和准确 completion | 保留原始 stderr/stream，诊断 CLI 参数/权限/解析器；不回退到 SDK 假装成功 |
| 2：Qoder CN edit | direct CLI 能否实际改一个允许文件 | 同一 adapter、同一模型，只将任务改为单文件 edit | diff、检查、结果和 ledger 全部一致 | 只分析本路线；不混入模型升级 |
| 3：Qwen3.8 | 3.8 是否被当前账号与 adapter 正确接受 | 复用阶段 2 的合同，仅换模型 ID | 与 3.7 相同的完成证据，并记录耗时/credits | 将 3.8 记为账号或版本受限，不替换默认 |
| 4：CodeBuddy 模型目录 | help、账号、ACP 实际接受 ID 是否一致 | 无修改握手；必要时一条最小 readonly ACP 任务 | 明确可用 ID 与证据时间 | 仅更新其模型登记，不影响 Qoder |
| 5：候选发布验收 | 用户下载后是否无需手工“再验证一次” | 同一 SHA ZIP 的候选 host 验收，按实际受影响 provider 执行一次 | 两个受影响 provider 的候选 receipt 完整，之后才可发布 | 停在 release incident，不重建或补发不同 artifact |

阶段 1 到 3 必须顺序执行；阶段 4 可以与阶段 1 并行；阶段 5 必须等所有实际改动冻结后执行。这样既不浪费积分，也不会把“模型、协议、发布包”三个变量混在一次失败里。
