## 本轮收口动作

修复仅允许 `EvidenceBootstrap` 的第一条冻结真实来源任务跳过“缺少 provider readiness tuple”这一项。它仍必须通过：running generation、installed plugin、plugin cache generation、marketplace activation、完整 durable plan/task、允许/禁止路径、独立 required checks、隔离 worktree、终态和 Codex 独立验收。

该例外不写入 readiness、不写入 accepted、不解锁后继任务；失败仍是失败证据。普通任务继续同时要求 readiness tuple 和同任务族 capability evidence。不得手改 plugin cache、readiness、active receipt、认证资料或 provider 数据库，也不得在默认 profile 绕过 health 门。

## 后续执行规则：不再无收益拆分

1. 一个连续验证批次只由一个执行上下文保有其 plan、worktree 和证据；V0、V1、条件性 V2 不在中途迁移或重复运行。
2. 只有当前对话还有一段不依赖该验证结果、且能独立完成的实现工作时，才并行拆出验证；否则当前对话不重复测试、不制造新分支，只等待可行动结论。
3. 验证回传必须只有三部分：确认了什么、没有确认什么、下一步唯一动作。当前回传的唯一动作即 host 刷新。
4. 本轮修复通过后，同一验证上下文以新候选 generation 连续恢复 Qoder 与 CodeBuddy V1 矩阵；当前对话只在 V1 形成结论后，集中处理共同产品根因、连接层决策和最终整合。
5. 若某 provider / 任务族不足 3 条真实 `accepted`，关闭该路径的 V2 与发布承诺；若两家都达标且存在可证实生命周期痛点，才做一次单变量连接层对照。

## 对产品路线的影响

本报告不改变公开能力、版本或发布范围。它只把一次实际运行暴露出的前置条件明确化：候选安装成功不等于 host 已加载候选 runtime；真实派工的首个门是新的 host `runtime_info`，不是重复 doctor、重复 dry-run 或放宽 health。
